# Changelog

All notable changes to this package are documented here.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), versions follow [Semantic Versioning](https://semver.org/).

## [2.2.2] - 2026-10-26

### Fixed

- **`World.Warmup` with a listener that destroys its temporary entity** (a "Health ≤ 0 destroys the entity" rule subscribed in `Init` fires on the default `Health`; any `IComponentListener<T>` or `IFilterListener` that destroys the entity it is handed) kept adding the remaining types to the freed slot. In release the next entity created there inherited those components, their mask bits and filter memberships (a singleton created in `Init` got a twin and `GetSingleton` threw); under `KENSEI_DEBUG` `Warmup` threw from `EcsBootstrap.Start`. If the listener also created an entity, which took the freed slot, every remaining type was added to it in both builds. `Warmup` now checks the temporary entity's handle before each type and continues on a new temporary entity when it is gone, and skips a type a listener already added to it (that threw "already has component"). Since 2.0.0.
- **Typed listeners that remove components of their own pool re-entrantly.** 2.1.1 kept one continuation slot per pool, so two linked entities whose `OnRemoved` removes the partner (`if (pool.Has(other)) pool.Remove(other)`) recursed until the stack overflowed (a native crash on IL2CPP), longer cycles did too (also across two pools), and with `DestroyEntity` instead of the `Has` guard the first listener got a second `OnRemoved`. Removals in progress are now a stack of frames: a nested `Remove` of a component whose removal is running continues that notification, every listener gets one `OnRemoved` per component, and a cycle ends. Since 2.0.0; 2.1.1 fixed only an entity removing itself.
- A component re-created in the slot it is being removed from is no longer taken for the old one. When an `OnRemoved` listener removes the component and adds it again (to the same entity, or by destroying the entity and creating one that reuses the slot), the outer `Remove` no longer removes the new component or destroys the new entity, and the new component's own removal notifies every listener (the first one was skipped). The same in `Add`: when a listener removes and re-adds the component, or destroys the entity and a new one takes the slot, the remaining typed listeners no longer get a second `OnAdded` for the new component. A removal also keeps the listener array it started with, so a listener that unsubscribes during it no longer makes the next one miss its `OnRemoved`. Since 2.0.0.
- **Adding `T` while a filter listener takes `T` away again left the entity out of `Exc<T>` filters it matches**: an `Inc<T>` listener that removes `T` in `OnEntityAdded`, an `Exc<T>` listener that removes `T` in `OnEntityRemoved` (the later `Exc<T>` filters lost it), a listener that destroys the entity and creates a new one in its slot, and a nested `Add<U>` that an `Inc<U>` listener rolled back (`Exc<U>`). The mirror of the 2.1.1 fix for `Remove`: after a filter whose listeners ran, the update stops when the entity no longer has `T` or its slot holds another entity. Since 2.0.0.
- **`CopyEntity` with a listener that destroys the copy** (an `IComponentListener<T>.OnAdded` or `IFilterListener` of a copied component: a spawn limit, a "Health ≤ 0 destroys the entity" rule) kept copying the remaining components into the freed slot. In release the next entity created there inherited them, with their mask bits and filter memberships (its component count said 1 with three components in the pools), and `OnEntityCreated` went out for the dead copy; under `KENSEI_DEBUG` `CopyEntity` threw with a message about int indices from a filter. When the listener created an entity, which took the slot, the remaining components and a second `OnEntityCreated` went to that entity in both builds. `CopyEntity` now stops when the copy is destroyed (it returns the dead handle and sends no `OnEntityCreated`) and when the source is destroyed (the copy keeps what it got and is created; an entity in the source's slot is not copied). `CreateEntity<T>` no longer sends `OnEntityCreated` for an entity that a listener of its component destroyed. `EcsEntityView.Spawn` skips the remaining providers when a listener destroyed the entity (it applied them to the freed slot, under `KENSEI_DEBUG` the next one threw) and binds the view to the dead handle. Since 2.0.0.
- `CopyEntity` of an entity inside the removal of its last component (from an `IWorldEventListener.OnComponentRemoved` or an `IFilterListener.OnEntityRemoved` of that removal, which run before the auto-destroy) created an alive entity without components: no filter saw it, nothing destroyed it, and world listeners got `OnEntityCreated` for it. Such a source has nothing to copy: `CopyEntity` now returns `Entity.Null` and creates nothing, in both builds. Since 2.0.0.
- **`World.Clear` from a listener inside `DestroyEntity`** (an `OnEntityDestroyed` or `OnRemoved` that restarts the level when the player dies) left the world broken: the destroy went on after `Clear` and released the slot again, so `EntityCount` was -1, the free list held a slot past the end, and the next entity created there was not alive (`IsAlive` false, its component on a dead slot, inherited by the entity after it); under `KENSEI_DEBUG` the next `Add` threw. An entity that the listener created after `Clear`, in the slot being destroyed, lost its components to the destroy. `DestroyEntity` now stops at a `Clear`, as `Remove` already did. Since 2.0.0.
- During `DestroyEntity`, `world.Has<T>` returned `false` for the components the destroy had not removed yet, although they were still in their pools, readable with `Get`, and got their own `OnRemoved` later: `if (world.Has<Position>(e))` in an `OnRemoved` of `Health` skipped silently, and `if (!world.Has<B>(e)) world.Add(e, …)` threw "already has component". A plain `Remove` did not do that. With component types in more than one mask word (over 64 types), removing a component of the dying entity could also put it into an `Exc` filter of that component, whose listeners saw it enter, until the components that made it match were removed. `DestroyEntity` now clears each component's mask bit as it removes it, and removing a component of a dying entity no longer lets it into a filter. A component that a listener adds to the dying entity still lets it enter the filters it then matches, now with the components not removed yet (`OnEntityAdded` sees it dead), until the destroy removes that component too; see `IFilterListener`. Since 2.0.0.
- **A pooled `EventBuffer<T>` list could end up on two entities.** A struct copy of the buffer stored again after its component was removed — through `Add`, `CommandBuffer.Add`/`Set`/`CreateEntity`, or the pattern 2.1.1 documented, `var b = world.Get<EventBuffer<Hit>>(e); b.Add(h); cb.Set(e, b);`, with a OneFrame cleanup (also of a nested runner) or a recorded `Remove` before `Playback` — put a list that was back in the static pool on the entity; the next buffer, in any world, got the same list, and the pool handed it out twice from then on (in a measured loop of the documented pattern after 2,000 frames: 15,964 duplicate pool entries, 28 entity pairs sharing a list, 132,800 B allocated over frames 1,001–2,000 instead of 1,704 B). The same happened, in any world, to a copy of another entity's buffer, also one whose list `world.AddEvent` had rented for a buffer the entity already had without a list (added as `new EventBuffer<T>()`, or set to `default`), and to a buffer forwarded from `OnRemoved` to another entity. Pooled lists now record whether they are free and which entity holds them (a pool id and an entity index): a value whose list is free or held by another entity is stored with an empty list of its own (`Count` 0, and `Values` is not `null`, so a reader that loops over `Values.Count` keeps working), an overwrite with such a value keeps the entity's buffer, a list returned twice is pooled once, and a list a stale copy appended to is cleared before it is handed out again. `world.AddEvent` records the entity as the holder of every list it rents. Every rent of a pooled list is numbered and the buffer that rents it keeps the number (in an internal field: `EventBuffer<T>` is 16 bytes instead of 8 on 64-bit), so a stale copy that holds a list rented again since, for a new buffer that is not stored yet (`var b = new EventBuffer<T>(); b.Add(x); cb.Add(e, b);`), is stored with the empty list and the new buffer keeps its events (in 2.2.1 both entities ended up with the list). Writes straight into the pool's storage (`Get(e) = copy`, `RawData`) and `pool.Get(e).Add(v)` on a buffer without a list (which rents a list without a holder) are not checked. Since 2.0.0.
- `CommandBuffer.Set` overwriting an `EventBuffer<T>` with a buffer that brings its own list returns the replaced list to the pool; it used to be dropped.
- `World.Destroy` kept the owning groups, and through them every owned pool's arrays, reachable from the destroyed `World` object.
- A `World.Reserve` that ran out of memory left the world unusable: it recorded the reserved sizes first, so every pool and filter created afterwards tried the same allocation and threw, and an interrupted growth could leave parallel arrays (slot arrays, a pool's dense arrays and change versions) with different lengths. Every array is now allocated before it replaces the old one, and the reserved sizes are recorded only after everything succeeded.
- `Filter.Reserve(n)` and the filter side of `World.Reserve(entities, n)` allocated up to twice `n`; they now size the dense array exactly, like pools. For `int.MaxValue`, which needs one slot more than an array can have, both throw `OutOfMemoryException` and change nothing; 2.2.1 did nothing for the filter, and in a world with filters but no pool `World.Reserve(…, int.MaxValue)` recorded the size anyway, so every pool created afterwards threw.
- When the rollback of a failed `SystemsRunner.Init` threw both inside a nested runner (a group or a phase, such as the `fixed` and `late` phases of `EcsBootstrap`) and in a runner above it, `Init` threw an `AggregateException` nested in another: `InnerExceptions[0]` was the inner `AggregateException`, not the original exception, and `Flatten()` listed the outer rollback errors first. It now throws one flat `AggregateException` at any depth: the original exception, then every rollback exception in the order they were thrown. Without rollback errors the original exception is still rethrown unwrapped; an `AggregateException` thrown by a system itself is kept whole as the original one.
- Under `KENSEI_DEBUG` a nested runner with a different `World` or `SharedData` was rejected only after its entry had been added to the parent; both checks now run before anything is registered. Registration errors name the method that was called (`SystemsRunner.AddPhase("fixed", SystemsRunner): ...`) instead of always `Add`.
- `SystemsRunner.Shared` of a runner added to a group or phase before that group was added to its own parent (a tree built from the bottom up, such as the groups `EcsBootstrap.Configure` adds to `fixedUpdate` or `lateUpdate`) returned the group's own empty `SharedData` from then on, while the runner's systems got the root's in `Init`. A runner without `SharedData` of its own now reads its parent's at every call. Under `KENSEI_DEBUG` a runner constructed with the root's `SharedData` and added to such a group before the group joined the root was rejected ("different SharedData than its parent"); the check now runs once the `SharedData` is known: when the runner, or a group holding it, is added under a runner constructed with `SharedData`, otherwise in `Init`. Since 2.0.0.
- `EcsBootstrap`: under `KENSEI_DEBUG` a system, group or phase that `Configure` registers in the update runner under `"fixed"` or `"late"` made `Awake` fail inside `AddPhase` with a message that did not mention `EcsBootstrap`. `Awake` now throws right after `Configure`, naming the system and saying that `EcsBootstrap` reserves these names for its phases. The phase names are unchanged, and the phases are still registered after `Configure` (initialized after the update systems, destroyed before them); release builds still check nothing.
- `EcsBootstrap`: `FixedUpdate` and `LateUpdate` run their runner only while that runner is initialized (they checked `Systems.IsInitialized`). When `Awake` failed before the phases were registered (an exception in `Configure`, or the reserved name above), every `FixedUpdate` and `LateUpdate` ran a runner that `Init` never reached: under `KENSEI_DEBUG` it threw each time, in release it ran systems that were never initialized, and in both it advanced the world tick on every call, like a root runner. Such phases now stay idle.
- `EcsEntityView.Spawn` called again before it returns — from a listener that the new entity's components trigger, such as an `IComponentListener<T>.OnAdded` or an `IWorldEventListener.OnEntityCreated` that spawns another view — no longer breaks the outer entity. Since 2.0.0 every call shared one static provider list, so the nested `Spawn` overwrote and cleared it: the outer entity lost the components of its remaining providers, and when the nested `Spawn` threw and the listener caught it, the outer entity got the child's providers instead. Each nesting depth now has its own list, reused by later calls, so `Spawn` still allocates nothing once warm; the list is also cleared when a listener throws.

### Changed

- **Behaviour change:** the rollback of a failed `SystemsRunner.Init` destroys only the systems whose `Init` completed and that implement `IDestroySystem`, at every nesting level. In 2.2.0 and 2.2.1 it destroyed every `IDestroySystem` registered before the failed system, so a system without `IInitSystem` (also one inside a nested runner that had completed its `Init`) was destroyed by the rollback: the retried `Init` and the frames after it ran with whatever its `Destroy` had released, and it was destroyed again at shutdown. Such a system now gets its `Destroy` only from `Destroy()` after a completed `Init`; a runner whose `Init` never succeeds does not destroy it, as in 2.1. Nested runners that completed `Init` are still rolled back system by system, the failing one still rolls itself back first, and the next `Init` still starts from the first system. The XML docs of `IInitSystem`, `IDestroySystem` and `SystemsRunner.Init`/`Destroy` describe the contract.
- **Behaviour change:** a `SystemsRunner` can be registered only once, in one slot of one parent, in every build. `Add`, `AddGroup`, `AddPhase` and the obsolete `Add(runner, name)` throw `InvalidOperationException` for a runner that is already registered — in the same runner (two groups, two unnamed slots, a phase and a group) or in another one — naming its slot (`the group "sim" (index 1) of this runner`), and for a runner added to itself or to a runner nested in it. A rejected call registers nothing. Up to 2.2.1 a second registration was accepted, and its slots shared the runner's `IsEnabled`: after `SetActive` on one slot the other slots, `IsActive` and `GetSystemInfo(i).IsEnabled` disagreed with what actually ran, so the Systems window showed wrong checkboxes; a runner added to itself recursed without end in `Init`. To run the same systems at two points of a frame, use two runners.
- **Behaviour change:** when a filter listener removes a component again while it is being added (or destroys the entity), world listeners get the `OnComponentRemoved` of that removal and no `OnComponentAdded` after it; up to 2.2.1 the `OnComponentAdded` followed and left them believing the entity had the component. The same for a removal: when a filter listener adds the component back while it is being removed (an `Inc<T>` listener in `OnEntityRemoved`, an `Exc<T>` listener in `OnEntityAdded`), world listeners get the `OnComponentAdded` of that addition and no `OnComponentRemoved` after it, and when it destroys the entity and creates one that takes the slot, they get the new entity's events and no `OnComponentRemoved` for the slot after them; up to 2.2.1 the `OnComponentRemoved` came last and told them the entity had lost the component, or that the new entity had. A world without filter listeners on the type pays nothing for it. Unchanged: a filter listener that removes the component and adds it back at once makes world listeners get the removal and then two `OnComponentAdded`, the re-added component's and the original `Add`'s, and a world listener that a filter listener subscribes during an `Add` or `Remove` gets that change's event.
- **Behaviour change:** a typed listener (`IComponentListener<T>`) that a filter or world listener subscribes during an `Add` of its pool gets the `OnAdded` of that `Add` only when the pool already had typed listeners when the `Add` started; otherwise its first `OnAdded` is for the next `Add`. Up to 2.2.1 it also got that `OnAdded` when the pool tracked changes, belonged to an owning group or held `EventBuffer<T>` (on a pool with none of these it did not either). With typed listeners present the `OnAdded` dispatch still starts after the filter and world listeners, over the listeners subscribed by then: one they unsubscribe gets no `OnAdded`, as up to 2.2.1.
- **Behaviour change:** the `ref` returned by `Add` points at the scratch value also when a listener destroyed the entity and a new entity took its slot; it used to point at the new entity's component. When a listener removed the component and added it to the same entity again, it points at the new component, as before.
- **Behaviour change:** a list assigned to `EventBuffer<T>.Values` by hand is still cleared when the component is removed, but no longer goes into the list pool.
- **Behaviour change:** under `KENSEI_DEBUG` a dead handle is accepted only for the entity whose `DestroyEntity` is running. It used to pass validation (`Add`/`Get`/`Has`/`Remove`, `AddEvent`, `pool.Add` by index) whenever any entity was being destroyed, so a listener inside some `DestroyEntity` could add a component or an event to another, dead slot, which the next entity there inherited.

### Performance

- `Add` no longer re-reads the dense index when no filter or world listener ran; `World.OnComponentAdded` takes a lean path while no filter of the component's type has listeners and nothing is dispatched (each type counts its listened filters, so a filter listener elsewhere in the world does not slow this type down); `World.OnComponentRemoved` handles world listeners out of line; `EventBuffer<T>` pools check list ownership on `Add` only, record the holder as a pool id and an entity index and call the check through a class instead of an interface; the re-entrancy frames store their listener arrays only when there is one to store (on IL2CPP every store into a reference field, `null` included, calls the GC write barrier). In-process A/B against 2.2.1 on an Apple M5, interleaved runs, medians: IL2CPP (Unity 6000.3.13f1, macOS arm64, Release, incremental GC with its write barriers; no device measured) / .NET 8 / .NET 10; runs of the same code differed by up to 2%, and by up to 4% for creating and destroying entities on .NET. Faster: `Add`+`Remove` without hooks −17% / −10% / −6%, with four `Inc` filters −4% / −5% / −6%, with four `Exc` filters −6% / −3% / −1%, the same four `Inc` filters next to a listened filter of another type −5% / −7% / −6%, with change tracking −13% / −4% / +3%; `DestroyEntity` of five components in filters −7% / −1% / −1%; `CreateEntity`+`DestroyEntity` and `CopyEntity`+`DestroyEntity` within ±3%. Slower, all with listeners or `EventBuffer<T>`: with a typed listener +26% / +20% / +24% (the re-entrancy frames, about 3 ns per `Add`+`Remove` on IL2CPP); through a filter that has a listener +19% / +17% / +17% (the re-check of the entity after each filter whose listener ran, about 2.5 ns); with a world listener +13% / −1% / −4% for `Add`+`Remove` (after the world listeners `Add` checks that the entity still has the component, and `Remove` reports through a separate method) and +10% / +12% / +4% for `DestroyEntity`; an `EventBuffer<T>`'s first event in a frame plus its cleanup +16% / +6% / +11%, three events +8% / +4% / +6% (the ownership check).
- `SystemsRunner.SetActive(bool)` on an inline group sets its slot directly instead of scanning the parent's run slots.
- What the last fixes of this release cost (the `OnAdded` dispatch taking the typed listeners after the world update, a removal reaching world listeners its filter listeners subscribed, numbered list rents), measured in-process A/B against the state before them on an Apple M5 Pro, .NET 8 / .NET 10, interleaved runs, medians; IL2CPP not measured, so the IL2CPP figures above predate them: `Add`+`Remove` with a typed listener +1% / +1%, with `Inc`, `Exc` or `Any` filters −1 to +2% / +1 to +3%, through a filter that has a listener and no world listener +3 to +6% / +2 to +3%; an `EventBuffer<T>`'s first event in a frame plus its cleanup +3% / +5%, a frame of OneFrame events +5% / +4%, the read-modify-write through `CommandBuffer.Set` +5% / +5%; the other paths measured (no hooks, change tracking, groups, world listeners, `CreateEntity`/`CopyEntity`/`DestroyEntity`) within ±2%.

### Generator

- **Behaviour change:** the generated `Init` is `public virtual` in every class that is not `sealed`, whether or not the compilation contains subclasses of it; a `sealed` class keeps the plain `public void Init`. In 2.2.0 and 2.2.1 it was virtual only when a subclass in the same compilation overrode it, so the `Init` a subclass in another assembly saw depended on the subclasses (and defines) of the base's assembly: with a subclass under `UNITY_EDITOR`, `DEVELOPMENT_BUILD` or `KENSEI_DEBUG`, the Editor chained a derived system and reported (KECS012) the `base.Init` that the player build needed, while the player silently kept the 2.1 layout with the base fields `null`, or failed with KECS006. A derived system in another assembly is now chained in every build, so a `base.Init` it still calls from `OnInit` for the 2.1 layout is KECS012: delete it. A hand-written subclass that declares `public void Init(World, SharedData)` without `override` or `new` gets CS0114 instead of CS0108 (both warnings; it still hides the base `Init`).
- **Behaviour change:** a derived generated `Init` fills the derived fields first, then calls `base.Init(world, shared)`, then the derived `OnInit`. 2.2.0 called `base.Init` before filling the derived fields, so the base `OnInit`, a hand-written base `Init` and the virtual methods they call saw the derived fields `null`; on 2.1, where the derived `OnInit` called `base.Init`, they were already filled. This corrects the 2.2.0 entries "base fields, base `OnInit`, then derived fields and `OnInit`" and "the base still runs first": the base `Init` still runs before the derived `OnInit`, but after the derived fields, as on 2.1. A `[Shared]` field of the derived class is now read before the base `Init` runs, so an object the base `OnInit` adds to `SharedData` is not there yet. Code that stood in `OnInit` before the deleted `base.Init` line runs after the base `Init`.
- **Behaviour change:** KECS006 again reports a class that keeps the 2.1 layout (lists `IInitSystem` over a base `Init` that cannot be overridden: not virtual, sealed, not public, hidden by a `new Init` in between, or from an assembly built by 2.2.1 or older) without a `base.Init` call, as 2.1.1 did, when the base `Init` would never run: it is the `Init` the runner reaches through `IInitSystem.Init`, or a base has injected fields (a `new Init` in between that does not implement `IInitSystem.Init`, with no injected fields above it, is taken for an unrelated method and not reported, as in 2.1.1); 2.2.0 dropped the check and the base `Init` with its injected fields was silently skipped. The check now also covers a hand-written non-virtual base `Init` that implements `IInitSystem` without injected fields, which 2.1.1 did not report, and a `sealed` or `protected` override of the base `Init` in a class between (`Mid : Root { public sealed override void Init(...) }`), which neither 2.1.1 nor 2.2.1 reported: the interface maps to the first declaration of the method, so the override was taken for an unrelated `Init` and both were skipped without a word. An explicit base `IInitSystem.Init`, which `base.Init` cannot reach, stays accepted without the call. Of a base in another assembly only the `protected` and `public` injected fields are seen, as for KECS013: over a base there with only `private` ones a missing `base.Init` is not reported.
- New warning KECS013: a hand-written override of a generated `Init` (directly or through hand-written overriding classes) that has no `base.Init` in its own declarations. On 2.1 such an override did not compile (CS0506); since 2.2.0 it compiled and left the base fields `null`. The check is syntactic like KECS012; a generated base in another assembly is recognised only by its `protected` or `public` injected fields.
- A hand-written base that implements `IInitSystem` through another interface (`GameSystem : IGameSystem` with `IGameSystem : IInitSystem`) and has a `public virtual Init` is chained; 2.2.0 reported KECS006 ("does not implement IInitSystem.Init") or, when the derived class listed `IInitSystem`, kept the 2.1 layout and skipped that `Init` without a warning. A derived class that lists such an interface itself keeps the 2.1 layout like one that lists `IInitSystem`. Whether a base `Init` is the one `IInitSystem.Init` maps to is decided by the compiler's interface mapping, now also for bases in other assemblies.
- The base `Init` is no longer picked by name and member order. An explicit `IInitSystem.Init` that does part of the base's setup and then calls the `public virtual void Init` next to it (`Init(world, shared)` or `this.Init(world, shared)`) is chained in either member order: the runner calls the explicit one, which reaches the generated override; 2.2.0 and 2.2.1 chained it only when the public `Init` came first. An explicit implementation that does not call the public `Init` is KECS006, since an override of the public one would never run (when the public one came first, 2.2.0 overrode it anyway and the generated `Init` never ran). The call is read from source, so a base from another assembly with both is KECS006. A generic `Init<T>(World, SharedData)` whose `T` the call cannot infer no longer gives a false KECS006 and does not take the generated `base.Init` call; a non-void `Init(World, SharedData)` between two chained classes is reported as an overload that takes the call instead of a misleading "is not virtual"; a private `Init` of a base is ignored.
- **Behaviour change:** such an explicit base `IInitSystem.Init` that does not call the public `Init` is KECS006 also when hand-written overrides of the public `Init` sit between the base and the derived class: the runner calls the explicit `Init`, so neither the overrides nor the generated `Init` run. 2.2.1 took an override for chainable, and the derived fields stayed `null` without a diagnostic. A base from another assembly is not read, so with an override in between it is KECS006 as well, also when its explicit `Init` calls the public one (2.2.1 compiled that, and it worked). A derived class that lists `IInitSystem` itself is chained over such overrides, as before (the interface then maps to the generated `Init`).
- **Behaviour change:** KECS006 also reports an `Init` overload on the chained base itself and on the classes above it, up to the class that first declares the overridden `Init`. C# looks an override up at that class, so an overload such as `Init(World, params SharedData[])`, `Init(World, object)` or `Init(World, SharedData, int x = 0)` above a hand-written `override` or next to it (or above a generated override of an `abstract` `Init`) took the generated `base.Init(world, shared)`, and the chained `Init`s never ran, without a word; 2.2.1 checked only the classes between. An overload in the class with the first declaration loses to it and stays allowed.
- A hand-written base with an `OnInit(World, SharedData)` of its own (for example a virtual hook its `Init` calls) no longer breaks the derived generated class: 2.2.0 declared the generated `partial void OnInit` over it (CS0114 or CS0108 in the generated file) and failed with CS0111 when the derived class overrode the hook. The generated part now declares no partial `OnInit` over such a member, and an override of the hook runs once, after the derived fields are filled: from the base `Init` when the generated `Init` calls a base `Init` that can call the hook (the hook is declared in that base or in one of its bases), and from the generated `Init` otherwise (a base that is not a system, an `abstract` base `Init`, a hook declared in a hand-written class between a generated base and the derived class). In the 2.1 layout an override of a hook that the replaced base `Init` can call is KECS006: the generated `Init` would call it, and the `base.Init` that `OnInit` must call would run it again (without end, unless guarded). A `partial void OnInit` that the derived class implements anyway is still declared and called, with the hiding warning silenced in the generated file. The same removes CS0108 for a system nested in its generated base. An `OnInit(World, SharedData)` written without `partial` (CS0111 before) is called by the generated `Init`, unless it overrides a hook that the chained base `Init` calls.
- Systems whose full names differ only in case (`Game.AI.MoveSystem` and `Game.Ai.MoveSystem`), or a generic system next to a class named like its hint (`Gen<T>` and `Gen_T_`), no longer make the generator fail. Roslyn compares hint names without case; the generator threw, the compilation got only the warning CS8785, and no system of the assembly had a generated `Init`, so all their injected fields stayed `null`. Such names now get a numeric segment (`Game.Ai.MoveSystem.2.Injection.g.cs`), chosen by the names, not by file order.
- Keywords used as identifiers (`namespace Game.@event`, `class @class`, a field `@event`, a type parameter `@in`) are escaped in the generated file; a keyword in a namespace or type name put `@` into the hint name and made the generator fail the same way (CS8785). A `[Shared]` key is written as an escaped string literal, so one with a line break or another control character compiles.
- No more CS0108, CS0109 or CS0505 in generated code over unrelated base members: a generated `Init` is declared `new` exactly when it hides an accessible inherited member (also a static `Init(World, SharedData)` or a non-method member named `Init`, which got no `new` before; not an `Init` with `in` parameters or an inaccessible one such as `private protected` in another assembly, which got a needless `new`), and a member named `Init` that is not a method on a class between two chained systems is KECS006 instead of CS0505 in the generated file.
- KECS012 says that the generated `Init` calls `base.Init` before `OnInit` (it said "first").

## [2.2.0] - 2026-10-22

### Added

- `EventBuffer<T>.Prewarm(lists, capacity)` fills the static list pool up front: the next `lists` lists the pool hands out get `Capacity` of at least `capacity`. Free lists already that large are used first, then the largest remaining ones are grown (at most `lists` of them, so a pool left large by an earlier peak is not inflated), and new lists are created only when fewer than `lists` are free; the prepared lists are moved to the top of the pool. A repeated call with the same arguments does nothing. The pool is static per `T` and shared by every world in the process; `World.Warmup` still does not fill it, and neither does `Prewarm` size the world (use `World.Reserve`).
- `World.Reserve(entities, components = 0)` grows storage ahead of time in one call: entity storage (generations, masks, free-slot list) and the sparse side of every pool and filter for `entities`, and the dense arrays of every pool (entities, data, change versions) and filter for `components`. Both apply to existing pools and filters and to those created later in the world. After `Reserve(n, n)`, creating and destroying n entities with components that enter filters allocates nothing; creating a pool or filter still allocates the object (and, in a new 64-type block, a mask word). `components` costs that many slots of every component type, singletons included; `ComponentPool<T>.Reserve(count)` (dense, data, change-version and sparse arrays) and `Filter.Reserve(count)` (dense array, safe during iteration) size one pool or filter. Nothing shrinks. On a destroyed world `Reserve` throws `ObjectDisposedException`.
- `World.GrowthsAfterReserve`: under `KENSEI_DEBUG` it counts every growth past what `Reserve` reserved (entity slots, free-slot list, pool sparse arrays and filter pages past `entities`; pool and filter dense arrays past `components`; a dimension left at 0 is not watched), and while `EcsProfiler` records the world each such growth is a `ProfileEventType.StorageGrown` event naming the array and its sizes (Profiler window: **Grow** filter). Its `EntityIndex` is -1. The window's search (`ProfileEvent.MatchesSearch`) treats a query of digits as an entity index and matches it only against events that have an entity, so typing `1` no longer lists every growth ("-1", "64 -> 128"); growth events are found by text (`dense`, a type name) or the **Grow** filter. Always 0 without the define; release builds check nothing.
- `Listeners<T>.Invoke(call, onError)` and `Invoke<TArg>(arg, call, onError)` call the listeners from a snapshot of the list in subscription order (first subscribed, first called; hand-written loops over `Values` usually went from the end). A listener removed from the list during the dispatch before its turn is skipped (a view destroyed with `Object.Destroy` stays subscribed until its `OnDestroy` at the end of the frame, so it is still called); listeners added during the dispatch are not called; each snapshot entry is called at most once. "Still subscribed" uses `Equals` like `Remove`, so a struct listener removed and added again counts as subscribed; a listener added several times is matched by value, not per copy. On an unchanged list the check is one reference comparison per listener; after a change the search widens from the previous listener's position in both directions, so a listener unsubscribing itself or a callback inserting listeners before the current one does not make the rest of the dispatch quadratic. If `onError` itself throws, the dispatch stops and that exception propagates. The snapshot is rented from `ArrayPool<T>.Shared` and cleared and returned in `finally`; nested calls work. Without `onError` an exception propagates; with it the error is reported per listener and the call continues. In the `TArg` overload `onError` is `Action<T, TArg, Exception>` and receives the argument too, so static lambdas for both `call` and `onError` allocate nothing.
- `SystemsRunner.AddPhase(name, runner)` registers a separate phase (same as the now obsolete `Add(runner, name)`); `AddGroup(name, runner)` registers a named inline group that runs inside the parent's `Run`, is reachable through `SetActive(name)`, `IsActive(name)`, `IndexOf(name)` and `GetRunner(name)`, and gives its name to its `ProfilerMarker` and `SystemInfo.Name`.
- `SystemsRunner.IndexOf(ISystem)` (by reference) and `IndexOf(string)` return the registration position used by `GetSystemInfo`/`SetActive(int)`, or -1. They find any registered system, Init/Destroy-only ones included, which `SetActive` cannot toggle (`GetSystemInfo(i).IsRunnable` is false). For a run system, group or phase `IndexOf(string)` resolves an explicit registration name exactly like `SetActive(string)`/`IsActive(string)` and falls back to the first unnamed system with that type name only when no system was registered under the name. Nested runners are not searched.
- `SystemsRunner.SetActive(bool)` toggles a runner through a reference to it: on an inline group (named or not) it switches the group's slot in the parent together with its `IsEnabled`, like the parent's `SetActive(name)`; on a phase or a root runner it sets the runner's own `IsEnabled` (a disabled root's `Run` still advances the tick but runs no systems).
- `SystemsRunner.OneFrame<T>(cleanWhenDisabled)`: with `true` the type is also removed in frames where the runner is skipped, at the slot of a disabled inline group (recursively into its inline groups) or in `Run()` of a disabled phase. Systems and `DelHere` of the skipped runner still do not run. `OneFrame<T>()` keeps the old behaviour. A runner tree without `cleanWhenDisabled` types passes disabled slots at the 2.1 cost.

### Changed

- **Behaviour change:** a `SystemsRunner.Init` that throws now rolls back. `Destroy` is called on every `IDestroySystem` registered before the failing system, in reverse order (a nested runner that fails rolls itself back first), the progress is reset and the original exception is rethrown; if rollback `Destroy` calls throw too, the rollback still completes (also inside nested runners registered before the failing system: each of their systems is destroyed even when another one throws) and an `AggregateException` holds the original exception followed by the rollback errors. The next `Init` starts from the first system. Up to 2.1.x the systems before the failing one were left initialized and the next `Init` resumed with the failing system. `Destroy()` after a failed `Init` does nothing.
- **Behaviour change:** `SetActive(index|name)` on an inline group (named or unnamed) switches both the parent's slot and the group's own `IsEnabled`; up to 2.1.x the unnamed child's `IsEnabled` stayed `true`. `GetSystemInfo` and `IsActive` agree with it. A direct `Run()` of such a group while its slot is off now runs nothing (it only removes `OneFrame` types registered with `cleanWhenDisabled`); in 2.1.x it ran the group's systems.
- Under `KENSEI_DEBUG` `SetActive(int)`, `SetActive(string)` and `IsActive(string)` on a system without `Run` (Init/Destroy only) throw `InvalidOperationException` saying so; `SetActive(int)` used to do nothing, and by name the error claimed that nothing was registered under the name. Release builds still ignore it. Names stay case-sensitive and an unknown name stays silent in release; both are now spelled out in the XML docs and on the runner page.
- `World.Filter` after `World.Destroy` throws `ObjectDisposedException`, and under `KENSEI_DEBUG` so do `CreateEntity` and `Pool<T>`, instead of a `NullReferenceException`.
- Under `KENSEI_DEBUG` registering a name that is already used in the same runner (system, group or phase) throws `InvalidOperationException`; before, the later registration silently replaced the earlier one in the name lookup. `AddPhase`/`AddGroup` throw for a `null` runner or an empty name in every build.
- `EcsBootstrap` registers its `fixed` and `late` phases with `AddPhase` instead of the now obsolete `Add(runner, name)`; the phases and their names are unchanged.

### Deprecated

- `SystemsRunner.Add(SystemsRunner runner, string name)` is a new overload marked `[Obsolete]` (a warning) with the 2.1 behaviour: a named runner passed to `Add` is a separate phase, which next to `AddGroup(name, runner)` reads like a group whose systems then never run. Use `AddPhase(name, runner)` for a phase or `AddGroup(name, runner)` for an inline group. `Add(runner)` without a name, `Add(system, name)` for other systems and a runner passed as an `ISystem` do not warn.

### Generator

- **Behaviour change:** a derived system with injected fields whose base can be chained (a generated base in the same compilation, or a hand-written base with a `public virtual` or `abstract` `Init`) always gets a generated `Init` that overrides the base one and calls `base.Init(world, shared)` first (none for an abstract base `Init`). A `base.Init` written in the class itself is now the new error KECS012 ("generated Init already calls base.Init first; remove the call from OnInit"): the 2.1 layout, where the derived class re-implements `IInitSystem` and calls `base.Init` from `OnInit`, is no longer kept for such classes. To upgrade, delete the `base.Init(...)` line; the base still runs first. The check is syntactic: any `base.Init` member access in the class's own parts counts, whatever overload it binds to (rename a hand-written base helper named `Init`); one inside a nested type does not. A class that lists `IInitSystem` itself over such a base without calling `base.Init` is chained too, so that base `Init` now runs (on 2.1 it was skipped). Over a base `Init` that cannot be overridden (not virtual, sealed, not public, explicit), a class that lists `IInitSystem` itself keeps the 2.1 layout as before.
- Systems with injected fields can derive from a `partial` system with injected fields in the same compilation, or from a base with a `public virtual Init`. The base's generated `Init` becomes `public virtual`, the derived one a `public override` that calls `base.Init`: base fields, base `OnInit`, then derived fields and `OnInit`. Works over several levels, through intermediate classes without fields and with generic bases. A hand-written subclass that overrides `Init` (directly or through hand-written intermediate classes that override it and call `base.Init`) also makes the generated base `Init` virtual, so such a chain compiles instead of failing with CS0506. Systems without inheritance get the same `.g.cs` as before. Where the generated `Init` hides an inherited one, it is declared `new` (no more CS0108/CS0114 in generated code).
- KECS006 is now reported only where inheritance cannot work: a base `Init` that is not virtual, sealed, not public or explicit (unless the class lists `IInitSystem` itself, see above), an intermediate class that hides `Init`, an intermediate hand-written class with another `Init` overload that the generated `base.Init(world, shared)` would bind to instead of the chained base `Init` (for example `Init(World, object)`, `Init(World, SharedData, int x = 0)`, a generic or `params` overload; rename it), or a base from another assembly whose `Init` is not virtual. The message names the reason. A derived class of a base that failed with its own error (for example KECS001) gets no second error.

### Fixed

- A typed listener that removes the same component again from `OnRemoved` (for example by destroying its own entity) corrupted the pool: the outer `Remove` swap-removed a slot that was already gone. The nested `Remove` now continues the notification from the next listener and does the removal, the outer one sees the component gone and stops; every listener gets one `OnRemoved`. Works with change tracking and owning groups.

The dense index is re-read before each typed `OnAdded` and before returning; a component removed before `Add` returns gets no further `OnAdded`, and the `ref` points at a scratch value whose writes are discarded.
- `CopyEntity` shared one `List` between the source and the copy for `EventBuffer<T>` and `Listeners<T>`; after the next OneFrame cleanup the pool could hand that list to two entities. Both now implement `IAutoCopy<T>` and give the copy its own list.

- `world.AddEvent` on a stale handle appended to the new occupant's buffer under `KENSEI_DEBUG`; it now throws like the other entity operations.
- An `IFilterListener.OnEntityRemoved` that added the removed component back left the entity out of the remaining `Inc` filters of that type.
- `World.Warmup` left its temporary entity alive, and world events suppressed, when a listener threw; both are now restored in `finally`.
- `World.Destroy` called twice threw; the second call is a no-op.
- `CommandBuffer.Set` on an existing component and a `CopyEntity` that overwrites a component (one a listener added during the copy) were invisible to change tracking; both now write through `Modify`. `Set` still does not run `AutoReset` on the old value, so writing back a modified copy (`var b = world.Get<EventBuffer<Hit>>(e); b.Add(h); cb.Set(e, b);`) keeps its list. `CopyEntity` runs `AutoReset` on the overwritten value for types with `IAutoCopy`, whose copied value owns its references.

- `Remove` tests the pool's `_autoReset` delegate instead of a `static readonly bool`, which IL2CPP does not fold and checks through class initialization on every call.

### Generator

- New errors for injection that compiled but left fields `null` at runtime or failed inside the generated file: KECS006 (a derived system where its own or the base `Init` would never run; deriving still works when the class lists `IInitSystem` among its bases if the base implements it, and calls `base.Init` from `OnInit` if the base has injected fields), KECS007 (no types in `[Inc]` and `[Any]`), KECS008 (a non-component type in a filter attribute), KECS009 (`readonly` injected field), KECS010 (`record` or `struct` system), KECS011 (system nested in a `record` or `interface`).
- KECS002 also covers an explicit `void IInitSystem.Init(...)`; KECS003 also covers `[Shared]` on a value type, which failed with CS0452 in the generated file.
- No false KECS003 on nullable-annotated fields (`Filter?`, `ComponentPool<T>?`) in a `#nullable enable` context.
- `Plugins/KenseiECS.Generators.dll` is rebuilt from these sources. The test that loads it now uses a separate load context (it used to get the generator project's own assembly) and checks a 2.1.1 diagnostic, so a stale DLL fails the tests.

### Editor

- Systems window repaints at most about 10 times per second instead of on every editor update.
- Profiler window caches the event snapshot (refreshed at most twice a second while recording, on enable/disable, after Clear and on entering Play Mode) instead of copying the buffer on every `OnGUI`, and keeps showing recorded events after the world is destroyed or recording stops.
- World Inspector counts components only for entities on the shown page (or for search matching), disables Next when no further match exists, and clamps the page when entities die.

### Documentation

- Generator diagnostics table, FAQ and migration guide list KECS006-KECS011 and the new KECS002/KECS003 cases.
- `ref` lifetime from `Get`/`Add`: any `Add` or `Remove` of the type on any entity invalidates it, and in an owning group any of the group's types does (components, groups, FAQ, architecture, XML docs).
- `EventBuffer<T>` allocates nothing only once its static, process-wide list pool has reached the peak; `World.Warmup` does not fill it.
- A disabled runner (or an unnamed child disabled through the parent's `SetActive(int, bool)`) does not clean its OneFrame/DelHere types; the unnamed child's own `IsEnabled` stays true.
- `World.Warmup` is visible to pool and filter listeners subscribed in `Init`.
- `EcsEntityView`/`SetName` without `KENSEI_DEBUG`: the call is an empty method, not compiled out.
- Benchmarks: measured on .NET 8 x64 only (no Mono, IL2CPP or ARM), the .NET build uses `BitOperations` while Unity uses the De Bruijn fallback, no `EventBuffer`/OneFrame scenarios, and "0 B" holds after capacities reach their peak.
- `CommandBuffer.Set` and change tracking pages describe the overwrite; `CopyEntity` overwrite and `AutoReset` are described under `IAutoCopy`.

## [2.0.0] - 2026-09-02

### Breaking

- `IComponentPool` replaced by the abstract class `ComponentPoolBase`. `Clear`, `AddDefault` and `CopyTo` are now internal; user code can no longer desynchronize masks and filters by calling them.
- `World.GetEntity(int)` on a dead slot returns the dead entity's own handle (`IsAlive` is false) instead of throwing under `KENSEI_DEBUG`. A slot's generation now changes when the slot is reused, not when it is freed.
- `IWorldEventListener.OnEntityCreated` fires after the first component is added (`CreateEntity`) or after all components are copied (`CopyEntity`). Listeners never observe an entity without components.
- `World.Unsubscribe<T>` keeps the empty `Listeners<T>` component; unsubscribing the last listener no longer auto-destroys the entity. `HasListeners<T>` is false for an empty list.
- `World.Remove<T>` no longer creates the pool for a type that was never added.
- `SystemsRunner.Destroy` runs `IDestroySystem.Destroy` in reverse registration order, is a no-op before `Init`, and resets the runner so `Init` can run again.
- `Listeners<T>` and `WorldListenerExtensions` moved from `Unity/` to `Core/` and no longer depend on Unity.
- The .NET project file moved from `KenseiECS/KenseiECS.csproj` to `KenseiECS.NET/KenseiECS.csproj`; the `KenseiECS/` folder is now a UPM package.

### Added

- `FilterBuilder.Any<T>()`: match entities with at least one of the listed types. `Any` and `Exc` of the same type is rejected; `Any` of an `Inc` type is dropped as redundant.
- `world.Filter<Inc<A, B>, Exc<C>, Any<D, E>>()` static filter specs (`Inc` 1-6 types, `Exc` 1-4, `Any` 2-4, `None`).
- `Filter.IsEmpty`, `First()`, `TryGetFirst`, `Single()`, `Entities` span, `AddListener(IFilterListener)` for enter/leave notifications.
- `ComponentPool<T>.AddListener(IComponentListener<T>)`: `OnAdded` after filters update, `OnRemoved` before AutoReset.
- `CommandBuffer`: deferred `CreateEntity`/`Add`/`Set`/`Remove`/`DestroyEntity` with `PendingEntity` handles, typed payload storage, zero allocations after warmup; commands on dead entities are skipped.
- `World.GetSingleton<T>()`, `GetSingletonEntity<T>()`, `HasSingleton<T>()`.
- `EventBuffer<T>` component and `world.AddEvent(entity, value)` for several events per entity per frame; lists are pooled.
- `KENSEI_DEBUG`: removing an entity from a filter that is being iterated throws when the swap-remove would make the loop visit an entity twice (nested loops tracked per enumerator).
- `KenseiECS.NET` multi-targets `netstandard2.1` and `net8.0`; the .NET build uses `BitOperations`.
- `SystemsRunner.GetSystemInfo(int)`, `SystemCount`, `SetActive(int, bool)`, `IsEnabled`, `World`: introspection for tooling. Every run system gets a `ProfilerMarker` on Unity; `LastRunMs`/`PeakRunMs` and `ResetTimings()` under `KENSEI_DEBUG`.
- `World.FilterCount`/`GetFilter(int)`; `Filter.IncludedTypes`/`ExcludedTypes`/`AnyTypes`, `ToString()`, `DenseCapacity`, `AllocatedBytes`; `ComponentPoolBase.SparseCapacity`, `DenseCapacity`, `ComponentSize`, `AllocatedBytes`.
- `World.SetName(Entity, string)` / `GetName(Entity)` debug entity names (`SetName` compiles out without `KENSEI_DEBUG`).
- Filter sparse arrays are paged (1024 slots per page, allocated on first touch); a filter no longer costs an `int` per entity slot of the world.
- Owning groups: `world.Group<T1, T2>()` (up to four types) keeps the owned pools' dense arrays aligned so members can be iterated through `Data1..DataN` spans with no sparse lookups. A pool belongs to at most one group. `World.GroupCount`/`GetGroup`.
- Change tracking: `pool.TrackChanges()`, `Modify(e)`, `MarkChanged(e)`, `ChangedVersion(e)`, `ChangedSince(e, version)` with `World.ChangeVersion` as the consumer's bookmark.
- `WorldSerializer`: `Save(world, stream)` / `Load(world, stream)` snapshots that keep entity indices and generations (so `Entity` fields inside components stay valid), identify types by name, write unmanaged components bit-for-bit and use `IComponentFormatter<T>` for components with references.
- Source generator (`KenseiECS.Generators`, shipped as `Plugins/KenseiECS.Generators.dll`): `[Inc]`, `[Exc]`, `[Any]`, `[Pool]`, `[Group]`, `[Shared]` on fields of a partial system class generate `Init` and call `partial void OnInit(World, SharedData)`. Diagnostics KECS001-KECS005 for misuse.
- `World.TryGetEntity(int, out Entity)`.
- `ParallelRunner` and `IRangeJob`: struct jobs over an index range (filter `Entities` or group `Data` spans) on fixed worker threads plus the caller, dynamic chunking, no allocations per `Run`, worker exceptions rethrown on the caller.
- Unity: `EcsBootstrap` base MonoBehaviour (World, SharedData, update/fixed/late runners, warmup), `IEcsSystemsProvider`, `EcsComponentProvider<T>` inspector-authored components, `EcsEntityView.Spawn(world)` and `EntityName`, `KenseiECS -> Systems` window with enable toggles and timings, Filters and Pools tabs in the World Inspector, debug names in inspector and profiler, `Samples~/BasicGame`.
- UPM package: `package.json`, `KenseiECS` and `KenseiECS.Editor` assembly definitions, committed `.meta` files. Install via git URL with `?path=/KenseiECS`.
- `ComponentType.TypeOf(int)` and `ComponentType.NameOf(int)` resolve the `typeIndex` passed to world event listeners.
- `World.GetComponentTypes(Entity, List<int>)`, `World.GetComponentCount(Entity)`, `World.GetPool(int)`.
- `ComponentPoolBase.ComponentType`.
- `SystemsRunner.DelHere<T>()` removes all `T` at that point of the pipeline; `SystemsRunner.IsInitialized`, `SystemsRunner.Shared`.
- `SystemsRunner.SetActive`/`IsActive` work on named child runners.
- `Listeners<T>.Count`.
- `IAutoReset<T>` and `IAutoCopy<T>` may be implemented explicitly.
- `KENSEI_DEBUG` validation: pool `Add` on a dead or never-allocated slot, `Run` before `Init`, `Add` after `Init`, unknown names in `SetActive`/`IsActive`/`GetRunner`, `GetComponentTypes` on a dead entity.
- GitHub Actions workflow running the test suite in both configurations.

### Fixed

- An exception thrown by a world event listener or `AutoReset` during `DestroyEntity` left a permanent zombie (dead flag set, components and filter membership intact, slot never freed). The slot is now always released and components are drained in `finally`.
- An exception in `SystemsRunner.Init` marked the runner initialized and skipped the remaining systems forever; `Init` now resumes at the failed system.
- An exception in a system skipped OneFrame cleanup, so events were processed twice; cleanup now runs in `finally`.
- `Warmup` fired world events and profiler records for its temporary entity.
- Removing a world event listener with a lower index from inside a dispatch invoked the current listener twice; the listener list is now copy-on-write.
- A child `SystemsRunner` constructed without `SharedData` got an empty container instead of the parent's.
- The World Inspector and EcsEntityView inspector lost edits made to nested structs and array elements.
- `KenseiECS -> Debug Mode` applied `KENSEI_DEBUG` only to the current build target group.
- `EcsProfiler` kept a static reference to a destroyed world and survived Enter Play Mode without domain reload.
- `Il2CppSetOption` did not apply to `Filter.Enumerator` (nested types do not inherit it), so the hottest loop kept bounds checks under IL2CPP.
- `ComponentPool.Clear` and `World.Clear` were O(entity capacity) per pool; sparse entries are now reset through the dense list.

### Changed

- Per-type filter lists are split into include/exclude/any, so adding or removing a component tests the mask only for filters it can move the entity into.
